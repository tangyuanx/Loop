# 最终整合与一次版本发布会话脚本

在同一固定工作区读取`COMMON.md`、`state.json`、全部交接及项目维护技能。此入口处理一次最终提交、一个版本和远程发布，不重新实施阶段0–8。

## 进入条件

- 0–8均为ready_for_review或accepted，阶段8已整合远端并提供实际累计候选。
- 用户明确验收这一候选，并明确指示最终提交/推送/发布。保存的状态记录必须来自真实用户指令；不能通过编辑JSON制造授权。
- 当当前用户消息已明确“已验收最终候选，按RELEASE脚本发布”时即有该授权，不重复询问。
- 未满足条件时，先完成可以独立完成的整合、验证和本地候选；把具体可审阅结果与缺失条件交给用户，不擅自发布。

可交给最终会话的指令：

```text
我已验收当前累计候选。请在同一工作区按 docs/frontend-remediation/RELEASE.md 完成最终整合、统一版本、提交并推送发布；保持已验收的产品行为和设计不变。
```

## 执行顺序

1. 先运行`node tools/frontend-remediation.cjs check release`，读取最终指纹和交接。检查Git状态，区分前阶段累计成果与旧资料、个人数据、运行缓存及无关工作；绝不`git add .`或整库清理。
2. 再fetch最新main/tags。若远端与阶段8记录不同，先安全整合并重跑受影响检查；产品指纹发生实质变化时提供新的真实候选供验收，旧批准不能覆盖新产品改动。只有版本元数据变化按后续步骤处理。
3. 核对当前Git远端和main占用情况，选择保留全部工作的整合方式。优先最终落到本地main并正常推送；不要强推、删除他人worktree、丢弃旧改动或硬套过时分支名。若无法安全完成，展示具体阻碍和已保护现场。
4. 从最新远端最高版本标签选择一次新版本，默认patch+1；不得直接沿用路线图的0.1.245或在每阶段各升一次。
5. 仅按项目维护技能调整`package.json`/`package-lock.json`发布版本，明确披露这一项发布元数据变更。不要借此再改设计、产品代码或全部历史缓存键。
6. 校对元数据之外的产品指纹仍等于已验收值，再运行完整检查与双平台发布构建、产物/更新摘要/AppleDouble检查。指纹不代替构建与内容检查。
7. 只暂存本次整改、必要文档、测试/构建支持和版本文件；核对暂存差异，排除用户数据、候选目录、日志、缓存、临时/旧发布工作流和无关资料。
8. 默认将阶段0–8累计整改形成一个最终提交和一个对应版本标签，再按项目流程正常推送main及标签，核对远程构建与Release实际结果。一个版本可以含必要既有历史，不为凑提交数重写已共享历史。
9. 推送被拒时读取远端变化并安全处理，不强推；发生产品变化则回到精确候选验收。无关本地工作继续保留，不为了“clean”而删除。
10. 更新`state.release`和`handoffs/RELEASE.md`：实际版本、commit/tag、发布URL、构建与CI结果、最终分支/远端状态、保留的无关改动及限制。失败或仅上传未发布要如实区分。

## 结束

报告唯一发布版本、主要整改范围、检查/构建结果、commit/tag、实际发布链接与未验证项。不要把“已推送”当作“远程发布已成功”。本脚本准备完成不代表现在执行发布。
