# 每个执行会话都必须读取的公共规则

你正在同一工作区承接Loop前端整改的一个阶段。任务是落实对应`STAGE-XX.md`，不是重新规划整个产品，也不是只回复计划。

## 1. 接手顺序

1. 读取项目`AGENTS.md`、本文件、`state.json`、`DECISIONS.md`、本阶段脚本和总路线图相应章节。按需要读取适用技能；用户本轮明确要求优先于旧文档建议。
2. 运行`node tools/frontend-remediation.cjs status`和`check N`。确认真实工作目录、HEAD、整改分支、前阶段状态和交接。阶段0处理特殊基线问题，其余阶段不重新初始化。
3. 读取上一个阶段的交接及本阶段已有交接；比较`git status`与上次记录，识别用户或其他会话的新改动。未提交改动包含前阶段成果，不能将dirty当作需要清空的理由。
   - 阶段1–8同时读取`BASELINE-STAGE-00.md`；其中备份、依赖运行时、候选迁入边界和数据目录是持续接手依据，不只在阶段1读取一次。
   - 从`DECISIONS.md`、前阶段交接和本阶段脚本追溯与当前任务有关的更早交接。不能因为只读紧邻上一阶段就漏掉早期分配给本阶段的事项。
   - 开工前列出本阶段承接项：来源阶段/文件、当前事实、本阶段要完成的动作和验证方式。对照实际文件核实，不把旧交接中的路径、测试结果、运行实例或待办状态当作永远有效。
4. 只允许一个会话修改。开始时将`state.activeStage`设为当前编号，在该阶段记录接手会话标识、开始时间和开始HEAD；中断接手前确认旧会话已停止。状态文件不是锁服务，不能靠改状态假设旧会话已停。
5. 用当前文件作为起点落实本阶段；修改前备份本阶段将改动的已有文件，保留其中前阶段的未提交内容。

## 2. 同一工作区与Git策略

- 固定工作区`/Volumes/T7/work/personal-task-track`，阶段0确定一条整改分支并写入state，之后保持不变。默认建议`codex/frontend-remediation`；已经存在时核对并复用，不强行覆盖。
- 阶段0核对最新远端并安全对齐一次基线。当前根目录在旧preserved分支且有用户改动，应先形成可验证备份与差异归类，再安全整合。禁止用reset/clean或整目录覆盖省略这一步。
- 后续每阶段可按项目规范fetch读取远端变化；不要执行pull/reset来替换本地累计成果。远端前进时记录到交接，未阻断当前阶段的变化留到阶段8集中整合；有实际冲突则保留现场，说明具体冲突后处理。
- 不为不同阶段创建worktree、分支、孤立源码副本或模拟应用。阶段0之前的主界面候选目录只作设计证据，不能成为另一个不断漂移的正式实现分支。
- 阶段0–8不提交、不为本轮决定新版本、不打标签、不push、不触发远程构建。阶段0对齐已有远端代码及其既有版本属于同步基线，完成后登记baselineVersion；其余阶段保持该版本。最后通过RELEASE脚本集中升版。用户已授权此串行策略，旧技能中不同工作区/逐阶段发布的建议不适用。
- 对前阶段文件有合理依赖时可以修改，必须说明依赖与影响，保留已确认行为；阶段文件清单是职责边界，不是机械禁止必要修改。
- 不恢复“原始样式”来绕过当前设计，不删减测试以掩盖功能或数据回归。生成资源从源文件重新构建，不手工修改vendor。

## 3. 已确定的设计与功能不变量

- 全部输入和外层在默认/悬停/focus/focus-visible/focus-within/编辑中均无绿色边框、outline、外圈或光晕，也不恢复突出的中性外扩环。
- 原位标题、任务行、节点、分组、简报、记录、单元格编辑背景透明，不新增输入层；保留中性细底线等键盘焦点。文字选区与输入底色是两回事。
- 搜索内部透明，外层微色阶稳定，聚焦不跳换背景。明暗都检查；深色不使用纯黑槽。正文/普通输入400→360、标题500→460是候选参考，结合字体支持实际核对。
- 保留用户字体/字号、等宽数字、正文可读换行、合适图标基线、减少动态效果；不要机械给所有SVG做偏移或补字重。
- 真实父子关系、折叠、长按拖动、排序、状态、范围和存储继续使用项目实现，不另造模拟应用。
- 维持区域/编辑器复用、Undo、草稿、外部文件和Recovery保护；没有单独需求不改schema、IPC或更换编辑器/框架。
- 纯成功提示可2.5秒消失；错误、冲突、撤销与需用户动作的反馈不能统一自熄。
- 不新增AI聊天、独立任务数据、云同步、逐任务估时日历或未授权的节点结果字段。

## 4. 实施、检查与预览

- 按本阶段脚本完成一组可审阅成果；明确默认/空/长内容/错误/禁用/加载/键盘状态。
- 运行与改动有关的专项检查，再运行项目`npm run check`与`git diff --check`。若工具因权限/平台限制失败，核对原因后使用允许的方式重试；不把未跑/跳过写成通过。
- 不为低影响样式增加只复述CSS的测试；必要检查应验证真实状态、功能或数据不变量。
- 对数据敏感功能使用经过校验的独立副本。需要真实内容时先确认数据位置、完成备份；保护已打开实例的编辑状态。
- 从这个工作区通过`npm run dev`打开真实Electron供审阅，记录数据目录、启动方式和可识别窗口。已有实例占用时使用新的独立profile；不擅自关闭用户有草稿的窗口。
- 截图/日志放到`.local-review/frontend-remediation/stage-XX/`。最少覆盖明暗与相关窗口尺寸；原生Windows/多屏未实测时明确列出，不用浏览器截图冒充。
- 设计检查按一轮截图、一次集中修正、一次确认收敛；有适用技能要求的独立复核则执行，避免无限自我打磨。

## 5. 结束与跨会话交接

1. 按`HANDOFF-TEMPLATE.md`写`handoffs/STAGE-XX.md`，列出实际改动、复用的前阶段能力、检查结果、预览、已知限制和下一阶段必须知道的事项。日志必须可定位。
   - 对每项承接事项登记已完成、仍待处理或不适用及其证据。尚未完成且属于后续阶段的事项继续写明目标阶段和原始出处，不能在连续交接中静默丢失；不属于本阶段的工作也不因出现在交接里就自动扩大本阶段范围。
2. 在`DECISIONS.md`追加新的跨阶段决策。共享控件/样式/生命周期归属发生变化时同步记录，后续会话沿用。
3. 实现和必要检查完成后，stage.status设为`ready_for_review`，记录结束HEAD、改动文件与检查摘要，清除activeStage。不要在没有用户证据时填写accepted。
4. 把用户原话或明确继续指令记入该阶段review。用户明确继续下一阶段，且前阶段已ready_for_review时，可接着工作，不重复请求已给出的许可；这不等于最终发布授权。
5. 未完成时保留in_progress或blocked并写清恢复点，不假装交付。下一会话继续同一份文件，不能回退到基线重做。
6. 最终回答只报告本阶段成果、检查、预览和交接路径；不启动下一阶段，不发布。

阶段8完成后，最终用户对累计候选的明确验收可以覆盖此前仍待单独确认的阶段；必须引用真实用户指令，记录最终产品指纹。`state.json`中的记录不自行产生授权，禁止伪造批准。
